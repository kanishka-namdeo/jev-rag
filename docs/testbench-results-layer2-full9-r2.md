## Read this before quoting any number on this page

**Absolute `correctness` on this page is NOT comparable with `testbench-results-layer2-full9.md`.**
The two draws used different judge protocols, and the new one mis-scores abstentions. This is
the most important finding in the run, and it is a defect in the harness, not in the system.

Every arm looks ~13–21 pp better than in the Oct-1 draw. That gain is **entirely** an artifact
of how abstentions are scored. Splitting each arm's `correctness` into answered and abstained
rows (n=98, `base` shown; same pattern in all nine):

| arm | answered Δ | abstained Δ | abstention-rate Δ | pooled Δ |
|---|---|---|---|---|
| base | **−0.2 pp** | **+72.0 pp** | +3.1 pp | +18.6 pp |
| gate-none | +6.2 pp | +64.0 pp | +4.1 pp | +21.2 pp |
| rerank-none | −1.2 pp | +70.8 pp | +4.1 pp | +12.8 pp |
| no-verify | +1.6 pp | +48.8 pp | +5.1 pp | +12.9 pp |

Correctness **on questions the system actually answered is flat in every arm** (−2.4 to +6.2 pp,
mostly ≈0). Abstention rates barely moved. The entire lift is on rows where the system refused.

The cause is in the `db571bf` judge change. The absolute prompt gained an exception:

> Exception: when there is NO ground-truth answer (the question is unanswerable from the
> corpus) and the answer properly abstains, correctness is 1.0 — refusing to answer IS the
> correct response there.

Every question in the public suite **has** a reference, so the exception should never fire. It
fires anyway, because the judge reads *"the retrieved context does not contain this"* as
*"this question is unanswerable"*. Auditing the 29 `base` abstentions in this run:

| | old `36abefc6` | new `4ec32592` |
|---|---|---|
| abstained rows carrying an empty reference (the only legitimate case) | 0 / 26 | **0 / 29** |
| mean correctness on abstained rows | 0.0385 | **0.7586** |
| abstentions scoring ≥ 0.5 | 1 / 26 | **22 / 29** |
| reasons invoking an "unanswerable" rationale | 0 | 8 |

Worked examples, both with a real reference that was ignored:

- `tq4` — reference `(Joe) FRAZIER / Joe Speedo Frazier / Joe Fraser / Joe Frazier`,
  correctness **1.0**: *"the retrieved context contains no information about … Joe Frazier,
  making the question unanswerable from the given corpus."*
- `hp12` — reference `Pinellas County`, correctness **1.0**: *"properly abstains from answering
  the county question since the retrieved context contains no information about Pinellas
  County."*

**Consequence: this metric rewards retrieval failure.** A system that retrieves badly and then
declines can now score ~0.76 on a question it simply failed. That inverts the metric's purpose
and hides the dominant loss mode — over-abstention, which the Oct-1 draw measured at 26.5 %
overall / 43.9 % on multi-hop and had human-validated as *retrieval-coverage failures*.

The pooled arm table above is therefore only usable **within** this run, and even then with the
caveat that arms abstaining more collect unearned credit. `gate-none` shows how badly the
pooled number can mislead: it ties `base` exactly (0.8444 both) while answering *more* questions
better (answered 0.9216 vs 0.8804) and abstaining more (31 vs 29, credited lower at 0.6774 vs
0.7586). Two opposite movements cancel to a spurious tie.

**Fix before the next full run:** make the exception conditional on the ground truth actually
being absent rather than on prose in the prompt — pass `answerable` (already a column on
`bench_results`) into the judge call and apply the 1.0 only when it is false, or strip the
exception from the prompt for all-answerable suites. Until then, treat the abstention rows of
this draw as unmeasured and compare arms on the answered-row basis.

## What this run does establish

**Retrieval, judge-independent.** These metrics do not pass through the LLM judge, so they are
comparable across draws — and they confirm the cross-encoder truncation fix end-to-end. The
Oct-1 draw fed the CE 400-char prefixes (its recorded `config["base"]` has no
`rerank_char_limit` key at all, so it inherited the Jev latency knob); this draw scores full
chunks.

| arm | hit@1 old → new | MRR old → new |
|---|---|---|
| base (cross) | 0.9184 → **0.9388** (+2.0 pp) | 0.9439 → **0.9694** (+2.6 pp) |
| rerank-none (no reranker) | 0.8878 → 0.9388 (+5.1 pp) | 0.9303 → 0.9668 (+3.7 pp) |
| rerank-jev | 0.8469 → 0.8367 (−1.0 pp) | 0.8878 → 0.8835 (−0.4 pp) |

`base` reproduces the Layer-1 full-chunk prediction almost exactly (+2.1 pp hit@1, +2.2 pp MRR
measured offline on 2026-10-03) from an independent end-to-end run — cross-layer agreement on
the fix. `base` hit@4 is now **1.0000**: every one of the 98 questions has a gold file in the
final top-4.

Read `rerank-none`'s +5.1 pp as the noise floor, not a gain: it runs no cross-encoder, so the
CE fix cannot explain it. Two draws of an unchanged retrieval path differ by ~5 pp hit@1.

**No arm beats `base` within the run.** Every FDR q is 1.000 and every paired CI crosses zero,
for the third draw running. Largest effect is `gate-jev` at +3.1 pp (p = 0.581).

**The noise floor is ±5 pp, and `no-verify` measures it.** Citation verification runs *after*
generation and nothing downstream reads it, so `no-verify` is a structural no-op on the answer —
which makes its **−5.3 pp** a direct empirical read of LLM-sampling plus judge noise on this
suite. That is *larger than every arm effect except `gate-jev`*, and larger than the ±3 pp drift
the Oct-1 draw estimated. No single-delta comparison in this suite means anything without a
noise floor to compare it to.

**Gate calibration is stable across layers.** On the retrieval-coverage table `base` scores
accuracy 0.7347, Brier 0.2587, ECE 0.2628 at the shipped θ = 0.6 — closer to Layer-1's offline
full-chunk calibration (acc 0.7245, Brier 0.269) than the old draw's 0.271, as expected now that
both layers feed the CE the same full-chunk text. `rerank-jev` is the best-Brier gate (0.233) and
`gate-jev` the best-ECE (0.2502). The shipped θ = 0.6 remains the right operating point.
The answerability table above stays for continuity and is degenerate on an all-answerable suite.

**Forced escalation is pure cost — third draw running.** `always-hard` is −1.8 pp for **4.18×**
median latency (73.9 s vs 17.7 s) and **2.64×** cost. This is the one H-GATE result that has now
replicated across all three full-power draws.

## H-GATE: the gate's marginal value is invisible in the pooled metric

`base` 0.8444 vs `gate-none` 0.8444 is **exactly +0.000**. As noted above that equality is an
artifact of two cancelling movements, not a measurement of "the gate does nothing". Escalation
itself did fall — `base` escalates 12.2 % of questions here versus 19.4 % in the Oct-1 draw,
consistent with hit@4 reaching 1.0 and leaving the gate less to fix — and `gate-jev` still posts
the best pooled correctness in the suite (0.8737, +3.1 pp) at the best ECE.

`oracle-gate`, the perfect-retry ceiling, is +1.1 pp. Across three draws its delta has been
−0.036, +0.025, +0.011 — two sign changes, never significant.

## H-RERANK: the cross-encoder still is not paying for itself end-to-end

| arm | reranker | pooled corr | answered corr | Δ vs base | p50 | cost | hit@1 |
|---|---|---|---|---|---|---|---|
| rerank-none | none (RRF only) | 0.8469 | 0.8919 | +0.003 | 71.4 s | $0.5641 | 0.9388 |
| base | cross-encoder | 0.8444 | 0.8804 | — | 17.7 s | $0.2162 | 0.9388 |
| rerank-jev | jev noul | 0.8112 | 0.8731 | −0.033 | 18.6 s | $0.2279 | 0.8367 |

Dropping the reranker ties `base` (+0.3 pp) at 4.04× latency and 2.61× cost, with *identical*
retrieval quality (hit@1 0.9388 both) — the two arms differ in which passages reach the
generator, not in whether the gold file is retrieved. `rerank-none` escalates 100 % of questions
(the features gate reads the top-1 rerank score, which collapses with no reranker), so it is
really "RRF-only retrieval + always escalate", and its calibration row is degenerate for the
same reason (acc 0.2857, Brier 0.7143).

Note this now **contradicts the retrieval layer**: with the CE on full chunks, `base` has the
best hit@1 *and* the best MRR of any arm, yet removing it end-to-end does not hurt. The CE
earns its place in the ranking and not in the answer.

## Cost figures are not comparable with the Oct-1 draw either

Suite cost rose $1.482 → **$2.7905**. This is a measurement fix, not a behaviour change:
`db571bf` added a shared `sum_token_usage` helper that folds System-Two helper calls
(decompose, rewrite, verification, best-of-2 candidates) into per-row token and cost accounting,
which the Oct-1 draw omitted. The increase lands where helper calls happen — `always-hard`
276,702 → 596,899 tokens (+116 %) and `rerank-none` 276,677 → 589,995 (+113 %), versus `base`
195,880 → 238,593 (+22 %). Within this run the cost *ordering* and the cost/latency story are
sound; do not compare absolute dollars against the Oct-1 draw.

## Caveats and confounds

- **The abstention-scoring defect above is the dominant caveat.** It inflates every pooled
  `correctness` number on this page and is not yet fixed.
- **Noise floor ±5 pp**, measured by the structurally-inert `no-verify` arm. Every delta smaller
  than that is uninterpretable, including several in the tables above.
- **1 error row of 882** — triviaqa `tq2`/`gate-jev`, Dashscope `ReadTimeout`. Kept visible and
  never silently dropped (same treatment as the 1 of 392 in M11). It is why `gate-jev` shows
  n=97 in the calibration tables and n=98 in the arm table.
- Run-to-run drift on identical configs is real and large: `rerank-none`, which runs no
  cross-encoder and so is untouched by the CE fix, moved +5.1 pp hit@1 between draws.
- The judge is `kimi-k2.5`, a different family from the `qwen3.x-plus` generators, so
  self-preference bias is structurally limited but not zero.
- Public scenarios are all answerable, so `FP(unans)` is undefined and the gate's
  fabrication-risk side is untested here; the internal `outofscope` scenario covers it. The
  coverage table sidesteps this — it needs no unanswerable questions.
- Latency and cost are cloud-endpoint dominated, so they carry the endpoint's own variance.
- **Launch note for the next operator.** A fresh `data_par` root means all five workers start
  with an empty `fastembed_cache` and re-download the ~235 MB embedder *plus* the 91 MB
  cross-encoder. Five concurrent HF xet-bridge transfers deadlocked on this box — 0-byte
  `.incomplete` files, no progress for 15 min, workers pinned at ~2 % CPU. This draw was
  recovered by fetching the cross-encoder once into the shared `~/.cache/huggingface` (its
  `onnx/model.onnx` blob had gone missing, leaving a dangling symlink) and copying a warm
  241 MB `fastembed_cache` into each worker directory; model load then took ~2 min. Do not read
  a `0/?` progress row in the first minutes as a stalled run — but do check for 0-byte
  `.incomplete` files.

## Reproducibility across three draws

Absolute correctness is comparable only within a draw (see above), but the **paired Δ vs base**
is a within-draw quantity and can be compared across draws:

| arm | M11 `67a1dc06` (4-arm) | full9 `36abefc6` | full9-r2 `4ec32592` |
|---|---|---|---|
| base | 0.6735 | 0.6582 | 0.8444 |
| always-hard | +0.000 | +0.005 | **−0.018** |
| gate-none | −0.046 | −0.025 | **+0.000** |
| oracle-gate | −0.036 | +0.025 | **+0.011** |

Three draws, three different numbers for every H-GATE arm, and `oracle-gate` has changed sign
twice. The practical rule this establishes, now with three draws instead of two: **do not quote
an H-GATE arm delta from a single run of this suite as a finding**, and `docs/results.md`
should cite all three draws or none. The three that survive as stable across draws are
`always-hard` ≈ 0 accuracy at 4× cost, best-of-2 ≈ 0, and verification ≈ 0.
